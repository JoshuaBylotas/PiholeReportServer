# Deployment

Three supported ways to host the site. Pick one; they are alternatives, not layers.

Whichever you choose, the same two rules apply:

- **Serve it over HTTPS.** Entra ID will not redirect to an `http://` reply URL other
  than `localhost`, and the session cookie must not travel in cleartext.
- **Never put secrets in `appsettings.json`.** Use environment variables (`__` as the
  section separator) or a certificate.

---

## Option 1 — IIS (most common on Windows Server)

### Prerequisites

```powershell
Install-WindowsFeature -Name Web-Server,Web-Asp-Net45,Web-Windows-Auth -IncludeManagementTools
```

Then install the **ASP.NET Core 10 Hosting Bundle** (not just the runtime — the bundle
includes the IIS module):

```powershell
winget install Microsoft.DotNet.HostingBundle.10
net stop was /y; net start w3svc      # required for IIS to pick up the module
```

### Publish

```powershell
dotnet publish src/PiholeReportServer -c Release -o C:\inetpub\PiholeReportServer
```

### Site and app pool

```powershell
Import-Module WebAdministration

New-WebAppPool -Name "PiholeReportServer"
# .NET Core runs out-of-process; the CLR must not be loaded into the pool.
Set-ItemProperty IIS:\AppPools\PiholeReportServer -Name managedRuntimeVersion -Value ""
Set-ItemProperty IIS:\AppPools\PiholeReportServer -Name startMode -Value "AlwaysRunning"

New-Website -Name "PiholeReportServer" `
  -PhysicalPath "C:\inetpub\PiholeReportServer" `
  -ApplicationPool "PiholeReportServer" `
  -HostHeader "<APP_HOST>" -Port 443 -Ssl
```

Bind a certificate for `<APP_HOST>` in IIS Manager, or:

```powershell
$c = Get-ChildItem Cert:\LocalMachine\My | Where-Object Subject -like "*<APP_HOST>*"
New-Item -Path "IIS:\SslBindings\0.0.0.0!443" -Value $c
```

### Configuration

`web.config` is generated by publish. Add settings via environment variables on the app
pool:

```powershell
$env = @{
  "ASPNETCORE_ENVIRONMENT" = "Production"
  "AzureAd__TenantId"      = "<TENANT_ID>"
  "AzureAd__ClientId"      = "<CLIENT_ID>"
  "AzureAd__ClientSecret"  = "<CLIENT_SECRET>"
  "AzureAd__Domain"        = "<TENANT_DOMAIN>"
  "AzureAd__RequireAppRoles" = "true"
  "Sql__Server"            = "<SQL_HOST>"
  "Sql__Database"          = "<SQL_DB>"
  "Sql__AuthMode"          = "SqlLogin"
  "Sql__UserId"            = "pihole_report_ro"
  "Sql__Password"          = "<PASSWORD>"
}
$i = 0
foreach ($k in $env.Keys) {
  Add-WebConfigurationProperty -PSPath "IIS:\Sites\PiholeReportServer" `
    -Filter "system.webServer/aspNetCore/environmentVariables" `
    -Name "." -Value @{name=$k; value=$env[$k]}
}
```

### Two IIS-specific gotchas

**Forwarded headers.** IIS terminates TLS, so Kestrel sees HTTP and generates
`http://<APP_HOST>/signin-oidc` — which Entra rejects as a redirect-URI mismatch.
`Program.cs` already calls `UseForwardedHeaders`; the ASP.NET Core Module sends the
right headers automatically, but if you front IIS with *another* proxy, that one must
send `X-Forwarded-Proto: https` too.

**Data protection keys.** By default the auth cookie is encrypted with keys stored in
the user profile, which an app pool identity may not have — so keys are regenerated on
every recycle and everyone is signed out. Fix it explicitly:

```powershell
Set-ItemProperty IIS:\AppPools\PiholeReportServer -Name processModel.loadUserProfile -Value $true
```

Or persist keys to a shared location (required if you ever run more than one instance):

```csharp
builder.Services.AddDataProtection()
    .PersistKeysToFileSystem(new DirectoryInfo(@"C:\ProgramData\PiholeReportServer\keys"))
    .SetApplicationName("PiholeReportServer");
```

Grant the app pool identity (`IIS AppPool\PiholeReportServer`) modify rights on that
folder.

## Option 2 — Kestrel as a Windows Service

Fewer moving parts than IIS, and a good fit for an internal tool.

```powershell
dotnet publish src/PiholeReportServer -c Release -o C:\Apps\PiholeReportServer
```

Add the service package to the project:

```xml
<PackageReference Include="Microsoft.Extensions.Hosting.WindowsServices" Version="10.0.0" />
```

```csharp
builder.Host.UseWindowsService();     // no-op when run from a console
```

```powershell
New-Service -Name "PiholeReportServer" `
  -BinaryPathName "C:\Apps\PiholeReportServer\PiholeReportServer.exe" `
  -DisplayName "Pi-hole Report Server" -StartupType Automatic

# Machine-wide settings, since a service has no user profile to read secrets from
[Environment]::SetEnvironmentVariable("ASPNETCORE_URLS", "https://+:443", "Machine")
[Environment]::SetEnvironmentVariable("AzureAd__TenantId", "<TENANT_ID>", "Machine")
# ... and the rest, as above

Start-Service PiholeReportServer
```

Point Kestrel at a certificate:

```jsonc
"Kestrel": {
  "Endpoints": {
    "Https": {
      "Url": "https://+:443",
      "Certificate": { "Subject": "<APP_HOST>", "Store": "My", "Location": "LocalMachine" }
    }
  }
}
```

The service account needs read access to the certificate's private key.

## Option 3 — Docker

```dockerfile
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS base
WORKDIR /app
EXPOSE 8080

FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY Directory.Build.props .
COPY src/PiholeReportServer/PiholeReportServer.csproj src/PiholeReportServer/
RUN dotnet restore src/PiholeReportServer/PiholeReportServer.csproj
COPY . .
RUN dotnet publish src/PiholeReportServer -c Release -o /app/publish

FROM base AS final
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "PiholeReportServer.dll"]
```

```bash
docker build -t pihole-report-server .
docker run -d --name pihole-reports -p 8080:8080 \
  -e ASPNETCORE_ENVIRONMENT=Production \
  -e AzureAd__TenantId=<TENANT_ID> \
  -e AzureAd__ClientId=<CLIENT_ID> \
  -e AzureAd__ClientSecret=<CLIENT_SECRET> \
  -e Sql__Server=<SQL_HOST> \
  -e Sql__UserId=pihole_report_ro \
  -e Sql__Password=<PASSWORD> \
  pihole-report-server
```

Terminate TLS at a reverse proxy in front, and make sure it sends
`X-Forwarded-Proto: https`. Without it, sign-in fails on a redirect-URI mismatch.

Data protection keys must be persisted outside the container or every restart signs
everyone out — mount a volume and call `PersistKeysToFileSystem`.

## Post-deployment checklist

| Check | Expected |
|-------|----------|
| `GET /healthz` **without** signing in | `200 Healthy` |
| `GET /` anonymously | 302 to `login.microsoftonline.com` |
| Browse `/` after sign-in | Overview with populated statistics |
| `/Diagnostics` | Correct SQL login, all six objects "Present" |
| A user *without* `Report.SqlAuthor` visits `/Query/Sql` | 403, and no SQL tab in the nav |
| Recycle the app pool / restart the service | Still signed in (keys persisted) |
| Run any report, then **Export CSV** | File downloads with matching row count |

> `/healthz` is intentionally anonymous so a load balancer can probe it. It reports
> process liveness only — it deliberately does not touch the database, so it will not
> flap when SQL Server is briefly unavailable. Use `/Diagnostics` to check database
> connectivity.

## Monitoring

```powershell
# Windows service state
Get-Service PiholeReportServer

# Recent application errors
Get-EventLog -LogName Application -Source ".NET Runtime" -Newest 20
```

For a lightweight availability check that covers the whole chain, poll `/healthz` for
liveness and query the warehouse directly for freshness:

```sql
SELECT DATEDIFF(minute, MAX(ts), SYSUTCDATETIME()) AS lag_minutes
FROM dbo.PiholeQueries;
```

Anything above ~5 minutes means the loader on the Pi-hole host needs attention — see
[the bad-row failure mode](05-pihole-sqlsync.md#the-bad-row-failure-mode--read-this-before-you-trust-restartalways).
